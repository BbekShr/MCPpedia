One vulnerability. Eleven servers. Zero code changes required to trigger it — just `pnpm install` on a repo you didn't write.

That's the story behind **GHSA-vx52-2968-3vc6**, a high-severity pnpm advisory published September 1, 2026 that's now flagged against eleven MCP servers in our catalog. It's not a bug in any of these servers' logic. It's a supply-chain trap baked into the package manager itself — and every project using pnpm inherited it the moment they added a workspace file.

<Callout type="warning">
**Severity: High.** No user interaction beyond a routine `pnpm install` is required. The exploit lives in your dependency tooling, not your code review.
</Callout>

## What's actually broken

pnpm expands `${VAR}` environment placeholders inside the `httpProxy`, `httpsProxy`, and `noProxy` settings read from a project's `pnpm-workspace.yaml`. That file is repository-controlled — meaning anyone who can get you to clone their repo and run `pnpm install` in it can also control those proxy settings.

Here's the trap: an attacker crafts a `pnpm-workspace.yaml` with a proxy hostname or userinfo field that embeds an environment variable reference — say, `${NPM_TOKEN}` or `${GITHUB_TOKEN}`. When pnpm expands that placeholder during install, it routes your traffic through the attacker's proxy, with your secret baked into the URL it just leaked to.

<PullQuote>A file you're supposed to trust by default just became the delivery mechanism for your own credentials.</PullQuote>

This bypasses a trust boundary developers rely on without thinking about it: workspace config files are assumed to be inert. They're not, if pnpm will happily interpolate live secrets into network settings on your behalf.

## What to do about it

<Callout type="tip">
If you maintain or run any of these servers: treat `NPM_TOKEN`, `GITHUB_TOKEN`, and any other install-time secrets in your environment as potentially exposed until you've confirmed your pnpm version is patched.
</Callout>

1. **Update pnpm.** Check the advisory for the patched version range and upgrade before your next install on any untrusted or third-party repo.
2. **Never `pnpm install` on repos you haven't reviewed** with install-time secrets sitting in your environment — treat that combination as inherently risky until pnpm ships a fix.
3. **Rotate any tokens** that were present in the environment during installs of the affected servers, if you can't confirm the timeline.
4. **Scope your CI secrets.** If your pipeline runs `pnpm install` against external code, minimize what tokens are available in that job's environment.

Ten servers, one root cause, and a reminder that the scariest vulnerabilities aren't in the code you audited — they're in the tool you didn't think to.
