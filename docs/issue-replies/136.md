Thanks for the detailed writeup — you had it exactly right, and the edit-history trace was genuinely useful for tracking down why.

The `is_archived` flag was set by our duplicate-detection bot, which picked the wrong row as the "keeper" when it found two rows pointing at your repo. The bot orders candidates by a `data_quality` score that, it turns out, nothing in our pipeline has ever actually computed — so in practice the tiebreak was random row order, not a real signal. That's fixed in [PR #142](#) (keeper selection now prefers a claimed/higher-scored/older row instead).

I've unarchived `io-github-makeev-alphai-mcp` directly and corrected its transport to `streamable-http` from the registry's current record. You shouldn't need to re-trigger schema/install extraction on your end — that's a separate pipeline and will pick it up on its normal schedule now that the row is live again.

One honest caveat: until PR #142 merges, a *future* duplicate-detection run could theoretically mis-merge a different server the same way. That PR is in review now.
