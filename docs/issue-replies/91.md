## Reply draft for issue #91 (net.convertica/mcp)

---

This is a thorough report, and you were right on both counts you flagged as bugs, wrong on one thing, and right that your two follow-on findings are real and worth fixing separately from the merge itself. Going through it in order:

**The merge itself:** fixed directly — `net-convertica-mcp` is unarchived; `net-convertica-mcp-2` was already gone by the time I looked (deleted, presumably by its own script or a later run), so there's nothing left to redirect. `homepage_url`/`api_*`/the claim never actually left this row — the archive banner and the search/sitemap exclusion were the only real damage, and unarchiving reverses both.

**Keeper selection (your finding #1):** confirmed as you diagnosed it. `data_quality DESC, id ASC` is exactly the ordering, and you were right that `data_quality` doesn't actually mean anything here — nothing in the codebase has ever populated that column, so the effective tiebreak was `id ASC` on a random UUID. Reordered to `publisher_verified DESC, score_total DESC, created_at ASC, id ASC` in PR #142, so a claimed/higher-scored/older row can no longer lose to an emptier one on a coin flip.

**Column merging (your finding #2):** partially stale, and worth correcting for the record — `homepage_url`/`api_name`/`api_pricing`/`api_rate_limits` *are* already merged onto the keeper before archiving (that shipped in an earlier PR, #92). What's still true and still a real bug: `publisher_verified` is not part of that merge, so the ✓ badge really does stay behind on the archived row. Fixed alongside the keeper-ordering change in PR #142.

**sync-registry parsing (your finding #3):** also stale — it already reads both the old and new registry field shapes (`registryType`+`identifier` as well as `registry_name`+`name`), so that particular parse bug is fixed. Your instinct that something's still wrong with *linked* rows was correct, though — it's just a different bug: the bot only refreshes two bookkeeping columns on a row it's already linked to a registry entry, never the actual data. Fixed in PR #138, which also covers your "why didn't the pre-insert guard catch this" question — the second row was a genuine duplicate insert, not a parser miss, and that's the specific failure mode PR #142's reordering + trust-flag transfer is meant to make survivable when it happens again.

One more thing your report surfaced that we're also fixing: the admin unarchive endpoint doesn't purge the 7-day page cache, so an unarchive like this one wouldn't actually show up on the live site for up to a week. Fixed in the same PR as the keeper reorder.

Thank you for the offer to send a PR — this round is already in progress, but I'll flag if anything above needs a second pass.
