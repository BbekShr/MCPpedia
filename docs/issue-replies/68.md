## Reply draft for issue #68 (datamcp)

---

Both halves of this were real bugs, thank you for the very precise writeup on each.

**FAQ / install metadata:** the generated FAQ was reading a `has_authentication` flag that was `false` even though `requires_api_key` was `true` on your listing — two different columns, and the FAQ text only ever checked the one that happened to be wrong for a registry-only remote server like yours. Fixed the flag directly (PR #137) and fixed the underlying logic so the FAQ won't assert "does not require authentication" from an unset flag going forward, and the install block now shows your hosted endpoint URL instead of a `<see-readme>` stdio stub for servers that are remote-only — PR #141. That required adding a `remote_url` column, since we weren't storing the actual endpoint the registry publishes at all before this.

**Sign-in-to-edit bug:** also confirmed and fixed. The edit page had a real race condition — it initialized to "no user" and never recovered if the initial auth check failed to complete before render, so a signed-in user landing on the page in exactly the wrong window would see the sign-in screen. Fixed in PR #140 by giving the page a proper loading state and subscribing to auth-state changes the same way the site nav already does correctly. You should be able to reach `/s/datamcp/edit` now — let me know if it's still not working after this deploys, since that would point at something more specific to your session.

- FAQ/install root cause: PR #141
- Edit-page sign-in bug: PR #140
